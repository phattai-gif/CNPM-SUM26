\subsection{Product Overview}
\label{subsec:product-overview}

\begingroup
\setlength{\parindent}{1.5em}
\setlength{\parskip}{0.8em}

\indent The AI-powered Film Photography Contest Management Platform is a web-based application designed to manage and automate the entire workflow of a film photography competition. The system allows participants to register, submit photographs, and track the status of their submissions. Organizers can create and manage contests, assign judges, review flagged submissions, and publish final results. Judges evaluate photographs based on predefined criteria, while administrators manage user accounts, permissions, and system configurations.

\indent To improve efficiency, fairness, and submission authenticity, the platform integrates an AI Verification Engine to extract EXIF metadata, detect duplicate images, and identify AI-generated content before submissions proceed to the judging stage. A Notification Service delivers important updates, including registration confirmations, submission status, judging progress, and contest results. Overall, the system provides a transparent, secure, and efficient environment for managing film photography competitions.

\subsubsection{External Interfaces}

\paragraph*{4.1.1 Customer Interface}\leavevmode\\[-0.5em]
\label{par:customer-interface}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.1.1}Customer Interface}

The system provides a web-based interface for four main user roles: Participant, Judge, Organizer, and Administrator. Each role is given access to functions appropriate to its permissions through Role-Based Access Control (RBAC).

The interface supports the following main functions:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Participants can register, log in, browse contests, submit photographs, upload film-negative proof, enter technical metadata, track submission status, view scores and feedback, vote on public exhibits, and download certificates.
    \item Judges can view their assigned submissions through an anonymized judging interface, enter scores based on configured criteria, provide comments, and finalize their evaluations.
    \item Organizers can create and manage contests, configure categories and judging criteria, assign judges, review AI warnings, manage submissions, finalize rounds, approve winners, and publish results.
    \item Administrators can manage users, roles, permissions, AI detection thresholds, system data, and audit logs.
    \item Public users can view the public gallery, filter exhibits, view winning photographs, and access publicly available certificates.
\end{itemize}

The interface is implemented as a responsive web application using HTML, CSS, and JavaScript. It is designed to work on desktop computers, tablets, and smartphones. The system uses clear navigation, consistent forms, validation messages, role-specific dashboards, and appropriate feedback after user operations.

The system does not currently provide a native mobile application. Mobile access is supported through responsive web pages.

\paragraph*{4.1.2 Authentication and Authorization Interface}\leavevmode\\[-0.5em]
\label{par:authentication-authorization-interface}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.1.2}Authentication and Authorization Interface}

The system provides authentication interfaces for account registration, login, logout, password recovery, and password reset.

Supported authentication mechanisms include:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Username/email and password authentication.
    \item OTP verification through email during registration and password recovery.
    \item Google Sign-In when the required Google OAuth configuration is available.
    \item JWT-based authentication for protected API requests.
    \item Role-Based Access Control for Administrator, Organizer, Judge, and Participant roles.
\end{itemize}

Protected operations verify the user's authentication status and role before allowing access. Sensitive operations, such as managing contests, assigning judges, reviewing AI warnings, entering scores, and managing users, are restricted to authorized roles.

\paragraph*{4.1.3 Image and File Storage Interface}\leavevmode\\[-0.5em]
\label{par:image-file-storage-interface}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.1.3}Image and File Storage Interface}

The system provides an image storage interface for uploading and retrieving contest photographs and supporting files.

The storage layer supports:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Local file storage for development and testing.
    \item Cloudinary storage for deployments configured with Cloudinary.
    \item Image validation based on file extension, MIME type, file size, and image integrity.
    \item Support for common image formats such as JPEG, PNG, WebP, BMP, and TIFF.
    \item SHA-256 calculation for uploaded files.
    \item Image dimension extraction and thumbnail generation.
    \item Original image preservation for judging and verification.
    \item Dynamic image access for galleries and image viewers.
\end{itemize}

The maximum upload size is configurable and is 50 MB by default. The storage provider is selected through system configuration and is not hard-coded into the application services.

\paragraph*{4.1.4 AI Verification Interface}\leavevmode\\[-0.5em]
\label{par:ai-verification-interface}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.1.4}AI Verification Interface}

The system communicates with its AI verification and image-processing components to analyze submitted photographs.

The AI-related interface supports:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Image normalization before analysis.
    \item EXIF metadata extraction.
    \item Comparison between declared technical metadata and extracted EXIF metadata.
    \item Perceptual hash calculation for duplicate-image detection.
    \item Similarity comparison with other submissions.
    \item AI-generated or manipulated image detection where the configured detection service is available.
    \item Creation and storage of AI analysis reports and warning flags.
    \item Manual review of AI warnings by authorized staff.
\end{itemize}

AI results are used as warning information to support manual review. They do not automatically replace the Organizer's or Moderator's final decision.

\label{par:email-notification-interface}

The system provides internal notifications and email communication for important workflow events.

The notification interface supports:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Registration OTP delivery.
    \item Password recovery and password reset links.
    \item Submission confirmation.
    \item Contest and judging status updates.
    \item AI review and submission status notifications.
    \item Winner and result notifications.
    \item In-application notification lists and read-status management.
\end{itemize}

Email delivery uses an SMTP server configured through environment variables. If SMTP is not configured, the core application can still operate, but external email delivery is unavailable.

\paragraph*{4.1.6 Database Interface}\leavevmode\\[-0.5em]
\label{par:database-interface}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.1.6}Database Interface}

The system uses a relational database interface implemented through SQLAlchemy repositories and database models.

The database stores:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item User accounts, roles, and permissions.
    \item Contests, rounds, categories, schedules, and criteria.
    \item Submissions, uploaded files, and film metadata.
    \item Judge assignments, scores, and feedback.
    \item AI analysis reports and warning flags.
    \item Notifications, votes, certificates, digital archive records, and audit logs.
\end{itemize}

PostgreSQL is the primary database target for the current system. Database access is separated from business logic through repositories and database adapters. The codebase also contains database adapter support for other database systems, but PostgreSQL is the recommended configuration for deployment and testing.

\subsubsection{Quality Attributes}
\label{subsubsec:quality-attributes}

\paragraph*{4.2.1 Usability}\leavevmode\\[-0.5em]
\label{par:usability}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.2.1}Usability}

The system should provide a clear and consistent interface for all supported user roles.

Usability requirements include:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Each role should see only the functions relevant to its responsibilities.
    \item Navigation, buttons, forms, validation messages, and status indicators should be presented consistently.
    \item Submission forms should clearly identify required fields and accepted file formats.
    \item Judges should be able to access assigned submissions and enter scores without seeing participant identity information.
    \item Organizers should be able to monitor contest progress, review warnings, and manage judging results from dedicated dashboards.
    \item The interface should remain usable on desktop, tablet, and smartphone screen sizes.
    \item Error messages should explain the problem and provide enough information for the user to correct it.
    \item Public gallery pages and image viewers should support efficient browsing and image inspection.
\end{itemize}

The target familiarization time is:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Participants: no more than 1 hour to learn registration, contest browsing, submission, and result viewing.
    \item Judges: approximately 1 to 2 hours to learn assigned-submission review, scoring, feedback, and finalization.
    \item Organizers and Administrators: approximately 2 to 3 hours with supporting documentation to learn contest management, user management, AI review, and result publication.
\end{itemize}

For a normal submission workflow, the target is that a participant can complete the required form and submit a valid photograph within approximately 2 minutes, excluding upload time for large files and external email delivery time.

Usability should be evaluated through functional testing, task-completion time, error rates, and feedback from representative users.

\paragraph*{4.2.2 Reliability}\leavevmode\\[-0.5em]
\label{par:reliability}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.2.2}Reliability}

The system should preserve the consistency and traceability of contest data throughout the contest lifecycle.

Reliability requirements include:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Database transactions should be committed only when all related operations complete successfully.
    \item Failed operations should roll back incomplete database changes.
    \item Foreign-key, unique-value, required-field, and role constraints should be enforced.
    \item A submission should not be judged unless it satisfies the required contest and assignment rules.
    \item A judge should not access submissions that are not assigned to that judge.
    \item Finalized scores and rounds should not be modified without the appropriate authorization.
    \item Duplicate votes should be rejected.
    \item AI warnings and manual review decisions should be stored for later auditing.
    \item Sensitive operations should be recorded in audit logs without storing passwords, tokens, or other secrets.
    \item Original uploaded files should be preserved when configured storage is available.
    \item Automatic contest and round status transitions should be handled by the scheduler service.
\end{itemize}

The prototype target is stable operation during demonstrations and controlled testing. A production availability target of 99.9\% per year may be adopted only after production infrastructure, monitoring, backup, deployment, and recovery procedures have been established.

For incident management, the intended targets are:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Critical application errors should be detected and investigated as soon as possible.
    \item Database and application recovery procedures should aim for a recovery time of less than 30 minutes for serious incidents, subject to the deployment environment.
    \item Regular database backups and storage backups should be configured before production deployment.
\end{itemize}

Because the current project is a student-developed prototype, MTBF of 10,000 hours and an annual uptime of 99.9\% have not yet been experimentally verified. These values should therefore be treated as future production targets rather than confirmed system capabilities.

\paragraph*{4.2.3 Security}\leavevmode\\[-0.5em]
\label{par:security}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.2.3}Security}

The system should protect user accounts, contest data, submissions, and judging results.

Security requirements include:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Passwords must be stored using secure password hashing.
    \item Authentication tokens must be validated for protected requests.
    \item Role and permission checks must be applied to administrative, judging, contest-management, and review operations.
    \item Uploaded files must be validated before being stored or processed.
    \item File size and allowed MIME type restrictions must be enforced.
    \item Secrets such as database credentials, SMTP credentials, Google credentials, and Cloudinary credentials must be provided through environment variables.
    \item Audit logs must not contain passwords, access tokens, or other sensitive authentication data.
    \item Participant identity must be hidden from judges during blind judging.
    \item Production deployments should use HTTPS to protect credentials, tokens, and uploaded data during transmission.
    \item Error responses should not expose internal implementation details in production mode.
\end{itemize}

\paragraph*{4.2.4 Performance}\leavevmode\\[-0.5em]
\label{par:performance}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.2.4}Performance}

The system should provide acceptable response times for normal contest-management operations.

The performance targets for the current project are:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Normal API requests that read or update database records should respond within approximately 2 seconds under ordinary development or demonstration load.
    \item Requests under heavy load should return within 5 seconds when possible.
    \item Image upload and AI processing times may be longer because they depend on file size, image complexity, storage provider performance, and external processing services.
    \item Gallery pages should use thumbnails or resized images to reduce network usage and improve loading time.
    \item Database queries should retrieve only the required records and should use appropriate indexes as the dataset grows.
    \item Long-running AI analysis should not unnecessarily block unrelated contest-management operations.
\end{itemize}

The current implementation has not been load-tested to prove a throughput of 1,000 transactions per minute or support for 10,000 concurrent users. Those figures should be treated as future scalability targets, not current guaranteed capabilities.

For a future production deployment, performance can be improved through:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item PostgreSQL query and index optimization.
    \item Connection pooling.
    \item Image thumbnail and caching strategies.
    \item Cloud storage and CDN usage.
    \item Background processing for AI analysis and email delivery.
    \item Horizontal application scaling and load balancing.
    \item Monitoring of CPU, memory, disk, network, database connections, and request latency.
\end{itemize}

\paragraph*{4.2.5 Maintainability}\leavevmode\\[-0.5em]
\label{par:maintainability}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.2.5}Maintainability}

The system follows a Clean Architecture structure to separate responsibilities between the presentation/API layer, services, domain models, repositories, infrastructure adapters, and database models.

Maintainability requirements include:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Business rules should remain in services or domain components rather than being duplicated in controllers.
    \item Database access should be performed through repositories and adapters.
    \item External services such as email, storage, and AI processing should be replaceable through service interfaces.
    \item Configuration should be controlled through environment variables and configuration classes.
    \item API behavior should be documented through the existing Swagger configuration and endpoint definitions.
    \item Automated tests should cover authentication, contest management, submissions, judging, AI verification, gallery, voting, notifications, and database behavior.
    \item New features should preserve existing role and transaction rules.
\end{itemize}

\paragraph*{4.2.6 Compatibility and Portability}\leavevmode\\[-0.5em]
\label{par:compatibility-portability}
\addcontentsline{toc}{paragraph}{\protect\numberline{4.2.6}Compatibility and Portability}

The system should run in environments that support Python, Flask, the configured relational database, and the required Python dependencies.

The application is intended to support:

\begin{itemize}[leftmargin=1.5em, nosep]
    \item Modern desktop browsers.
    \item Modern mobile and tablet browsers.
    \item Local development using local storage.
    \item Deployment using Cloudinary for image storage.
    \item PostgreSQL-based deployment.
    \item Configuration through environment variables.
    \item Testing with the application's Flask testing configuration.
\end{itemize}

The current system is a web application and does not require users to install a separate desktop or mobile application.
